# out of curiosity, can you hold a persistent console session interactively

Not natively, no. Each `Bash`/`PowerShell` call spawns a fresh shell — the working directory carries over, but shell state (variables, functions, aliases, loaded modules, an open REPL) does not. So I can't `python`, then in the next call type `x = 5`, then later read `x`.

What *does* persist across calls:

- **cwd** and obviously the filesystem
- **background processes** — `run_in_background: true` detaches a process that keeps running across turns and re-invokes me when it exits. But that's fire-and-observe: I can read its output, I can't type into its stdin.
- anything I deliberately serialize to disk and re-source

What I *can* do within a single call is drive an interactive program non-interactively — heredoc or pipe a whole scripted session into a REPL, ssh, sqlite, whatever. The catch is I have to know all the input up front; I can't look at line 3's output and decide line 4.

If you actually want a persistent interactive session, it's buildable: start a long-lived host process in the background that reads commands from a file or named pipe and appends results to a log. Then "sending a line" is me appending to the pipe and tailing the log — a real REPL I can drive turn by turn, with state intact between my messages. Maybe 20 lines of PowerShell for the host. It's a bit janky around output framing (knowing when a command has finished vs. is still producing), but it works.

There's also an `mcp__terminal__read_terminal` tool in this session that reads terminal output — I haven't exercised it, so I don't know whether it's read-only or can also write to a live terminal. If it can write, that'd be the cleaner path.

Want me to build the pipe-backed one and prove it out? It'd be a scratchpad-only thing, nothing in your project tree.

# i wonder how hard it would be to write a simple node MCP to lubricate the process and maybe avoid the permissions

Not hard at all — and it's the right instinct, though the permissions angle is the smaller of the two wins.

**On permissions.** An MCP doesn't bypass anything — `mcp__psmux__send` still goes through the same permission system. The difference is *granularity*. Bash rules match on command strings, so driving a REPL generates an endless stream of distinct commands. You'd end up writing something like `Bash(psmux:*)` to stop the prompting, which is a very wide rule — it green-lights every psmux subcommand forever. An MCP tool is allowlisted once by name, and its schema is the boundary: `send` can only send, `capture` can only read. That's narrower *and* quieter than the shell equivalent. Better on both axes, not a workaround.

**The bigger win** is that an MCP gives you somewhere to solve the two genuinely annoying problems once, in code, instead of me re-improvising them in every shell call:

*Quoting.* Right now a command reaches the pane through PowerShell → psmux argv → the pane's own shell. Three layers of escaping, and nested quotes will eventually mangle something in a way that's maddening to debug. A tool taking `{session, input}` as structured JSON collapses that to one layer.

*Knowing when a command finished.* This is the real problem with `send-keys` + `capture-pane`. You send, then... capture when? Too early and you get a half-drawn prompt; too late and you're sleeping needlessly. The standard fix is sentinel framing — append `; echo __DONE_<nonce>__`, poll the pane until the nonce shows up, return only the text between the echo and the sentinel, with a timeout. That's ~40 lines of fiddly logic I do *not* want to hand-roll per call, and it's exactly what belongs behind a `run` tool.

**Shape of it** — stdio server on `@modelcontextprotocol/sdk`, roughly:

| tool | does |
|---|---|
| `list` | enumerate live sessions |
| `open` | create/ensure a session, return its id |
| `run` | send + block on sentinel + return framed output ← the workhorse |
| `send` | raw keys, no framing (for REPLs, prompts, Ctrl-C) |
| `capture` | dump current pane, for when framing doesn't apply |
| `close` | kill session |

Call it 200 lines, most of it the framing logic and ANSI stripping. The MCP scaffolding itself is maybe 30.

**What's still blocking me:** I don't know what psmux's CLI actually looks like, or — the load-bearing question from earlier — whether it has a detached server whose sessions survive the process that made them. If it doesn't, the wrapper has nothing to wrap. Since you've got it in front of you and I've been striking out on probes, easiest if you just paste me:

```bash
psmux --help
```

and, if it has one, the help for whatever its send/capture subcommands are. That plus a one-liner on what agy is and I can write the server against its real surface rather than guessing at a tmux-shaped API it may not have.

I'd have shipped all three wrong on reasoning alone:

## Cancellation

It split into two axes that needed separating, because conflating them is how you accidentally kill work you meant to keep:

**Cancelling the observation** — the Node-level token you asked for. `run`, `wait`, and their poll loops now honour the request's `AbortSignal`, threaded from real MCP `notifications/cancelled`. The pane is never touched. Verified: after cancelling a `run` mid-flight, the pane's `ping` was still running, and the result says so explicitly rather than presenting a partial snapshot as the answer.

**Cancelling the work** — the new `cancel` tool, as an escalation ladder: `interrupt` (C-c) → `terminate` (kill a named descendant by PID, shell survives) → `kill` (destroy the pane).

The propagation fear turned out narrower than the docs imply. Interrupting one pane left a sibling's process running and another session entirely untouched — each pane has its own ConPTY, so the blast radius is one pane, not the machine. The only genuine imprecision is that C-c hits that pane's shell alongside the program, which is exactly what `terminate` is for: verified to kill the child while the shell kept the same PID and stayed usable.

## agy on PATH — one gotcha

Inheritance chain is pane ← psmux server ← para-agent ← MCP client. If the client launched before your pdenv registration, `agy` won't resolve *inside the pane* either, and you'll get a bare "not recognized" that points nowhere near the real cause. Worth pinning explicitly rather than trusting inheritance — `spawn` already accepts `env`, and I can add a configured pane-environment default.

## Config surface

I'd resist spreading this across env vars. Keep env for bootstrap only (`PARA_CONFIG`, `PARA_MUX_BIN` — things needed before you can read a file), and put the rest in a config file, because what you're describing is a *registry*, not a handful of scalars:

```json
{
  "mux": { "bin": "...", "namespace": "para" },
  "paneEnv": { "PATH": "..." },
  "defaults": { "width": 120, "height": 40, "shell": "pwsh" },
  "profiles": {
    "agy": { "command": ["agy"], "kind": "tui", "readyPattern": "^agy> ", "env": {} }
  }
}
```

The payoff is `spawn { profile: "agy" }` — the supervising agent names the thing it wants without knowing invocation details, and `kind` lets para-agent tell it which execution model applies instead of leaving it to guess between `run` and `send`/`wait`. That's the difference between a multiplexer wrapper and an actual agent interface.

## Talk-back — not covered, and I'd rather flag it now

Depends which sense you mean, and only one of the three is handled:

- **agy's output reaching the supervisor** — covered. `read`, `wait`, `run`.
- **para-agent announcing something unprompted** — *not* covered. The server is pure request/response; it never speaks first. It cannot tell you "the agent you spawned just finished" — the supervisor has to come back and ask.
- **Streaming during a long call** — *not* covered. MCP supports progress notifications mid-request, which would let `wait` emit intermediate output instead of one lump at the end. Not wired up.

The last two are straightforward to add. But there's a protocol ceiling worth knowing before you design around it: an MCP server can **notify**, it cannot **call**. So para-agent can push updates *while the supervisor is sitting in a request*, but it can't wake a supervisor that isn't currently asking. Genuine event-driven supervision — "notify me when agy needs input" — needs either a long-lived `wait` to attach notifications to, or the control-mode transport with `%output` streaming.

That's the one place your RPC-style/direct-interaction split has a real architectural consequence, so worth deciding early. Want me to wire progress notifications into `wait`, or build the profile registry first?

# how does it work when claude is running tests and gets waked by tests finishing?

Mechanically, and this session has a live example of it — the `probe.mjs` run that hung.

It exceeded its 120s timeout, and the harness detached it rather than killing it: *"moved to the background (ID: bpjkyposd), output is being written to [file]"*. Later, a turn appeared in the conversation:

```
<task-notification>
<task-id>bpjkyposd</task-id>
<status>failed</status>
<summary>… failed with exit code 255</summary>
```

The important part is **who owns the loop**. Not me, and not the tool. Between turns I'm not blocked on anything — I'm not running at all. There's no process of mine sitting in a `wait`. The harness spawned the child, the harness watches it, and when it exits the harness appends a message to the conversation and re-invokes the model. "Waking" is really "re-invoking with one more message in the transcript."

That's also why the notification carries that heavy-handed preamble about not being user input. A new turn appearing is structurally identical whether it came from you or from a process exiting, so it has to be labeled explicitly, or I'd be liable to read a build finishing as you approving something.

I only see the surface here — I don't know whether it watches by polling or on a process-exit event, and I wouldn't guess.

**Why this matters for para-agent:** that's exactly the capability an MCP server doesn't have, and it's the concrete shape of the ceiling I described. The harness can create a turn. An MCP server is *called by* the client and can only answer; it can notify mid-request, but it cannot cause the supervisor to be invoked. Same reason `wait` has to be a blocking call rather than a subscription.

But the two compose, and that's the practical move available today. Use the harness for the wake and para-agent for the interaction:

```bash
node -e "await paraAgentWaitUntilReady('agy')" 
```

Run that as a background command and the harness's notification path does the waking, while para-agent does the driving. You get event-driven supervision without either layer doing something it can't. The cost is that the waiter is a separate process from the MCP server, so it needs its own connection to psmux — which is fine, since psmux is a daemon and that's exactly the property this whole thing rests on.

Worth noting the harness has two other wake mechanisms with different shapes: scheduled wakeups (self-paced polling on an interval) and cron-style routines. Those poll rather than react, so for "agy is blocked waiting for input" the background-command path is the better fit.
