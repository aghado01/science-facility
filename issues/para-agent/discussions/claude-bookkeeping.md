# and regarding blocking vs handle return, i favor async handle and furthermore want to incorporate a built in feature for arming an awake signal like i've seen you set manually during a session

Async handle is the choice I'd have voted for from the driver's seat — the 6–13 minute turns are exactly the span where I'd otherwise sit blocked while there's triage prep, brief drafting, or other lanes to advance. And the awake-signal arming is the piece that makes the handle model actually pleasant rather than polling-with-extra-steps.

Worth distinguishing the two mechanisms you've seen me use, because they're different qualities of signal and the built-in should model the better one. What I set manually with the scheduler is the weak form — a timer that guesses when to check back, which is just polling wearing a nicer coat; pick the interval wrong and you either wake early for nothing or leave a finished turn sitting idle. The strong form is what the harness does with background tasks: the work itself fires the notification when it completes, no interval guessing at all. Para-agent is perfectly positioned for the strong form, because it — unlike me watching a pane — actually knows the moment the headless process exits. So "arming" ideally means: exchange tool returns the handle, and completion itself pushes the signal, with a timer only as the fallback heartbeat for hung turns — which is precisely the shape of the L4 fix. The completion-signaling primitive from the friction list and this arming feature are one piece of infrastructure seen from two sides: the MCP detecting completion is the mechanism, the armed signal is its delivery.

One delivery-side note: the signal has to land in the primary's harness, not just exist in para-agent's state. When the primary is a Claude Code session, the native hook is the task-notification path — a wait-on-handle tool the harness tracks as background work gets the strong-form push for free. A file-sentinel or journal flag works as the transport-agnostic fallback for primaries whose harness can't be pushed to. Designing arming as "para-agent knows completion; delivery adapts to the driver's harness" keeps the feature portable across whatever sits in the primary seat later — including the local-gguf workers, whose harness will be yours to define anyway.

# yea. and i believe there should be an client agnostic abstraction for this that can be handled by the back-end and captured in client-specific adapter and config profiles that contain the implementation details for each client's harness

That's the same shape that's already worked once in the ecosystem — the governance plane prototype landed as exactly this split: a client-agnostic contract with a Claude adapter carrying the harness-specific mechanics. So there's house precedent for the pattern, and it's proven at small scale.

It also unifies nicely with the config architecture you've been sketching across this conversation. The backend owns the semantic vocabulary — turn completed, deposit written, turn hung past heartbeat — and emits those events against the journal spine's turn identity, without knowing or caring who's listening. The adapter profile owns the verbs: for a Claude Code primary, "completed" becomes a task-notification push; for a pane-only or gguf driver, it becomes a sentinel file or journal flag; for a future harness, it's whatever that harness natively consumes. That's the same declaration-versus-projection move as the shared-MCPs section — one authoritative statement in config, per-side mechanics generated from it — and it slots into the same profile file, so a client profile ends up describing one seat completely: which shared MCPs it mounts, how signals reach it, what its harness quirks are. The adapter layer even becomes the natural home for the probe discipline from L1: each profile can declare how to verify its client is actually reachable, so a misconfigured seat fails loud at arming time instead of silently never waking.

The design test I'd keep in view as it firms up: the backend's event vocabulary should stay small and closed while the adapter set stays open. If adding a new client ever requires touching the backend's event semantics, the abstraction has leaked — everything client-shaped belongs in the profile.
