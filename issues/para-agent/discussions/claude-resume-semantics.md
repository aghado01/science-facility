
# another thing is session resume semantics. agy makes it pretty clear by announcing 'use blah blah to resume session' and that can be recorded systematically, but the equivalent for other clients needs to be captured in profiles too as part of their respective adapters, so the MCP can speak one language for resume semantics

Resume is a particularly good candidate for this treatment because it's currently the most leaked client detail in the whole pattern — the established form in my field notes is literally "scrape SESSION_ID out of the receipt, pass `--resume <id>` next turn," which is claude-CLI mechanics living in driver knowledge. Under the abstraction, the driver-facing verb is just "continue this thread," addressed by the journal spine's turn identity, and the adapter translates that into whatever its client needs. The resume token then becomes a recorded spine field rather than something announced in stdout and hopefully caught — which incidentally solves the two-identity-systems join problem I described earlier, since the claude session id gets captured as an attribute of the turn record instead of floating in a parallel numbering universe.

The one thing the profiles will need beyond token syntax is a declaration of what kind of continuity each client can actually offer, because clients differ in what resume _is_, not just how it's spelled. Claude's session id is durable native resume across process exits. A local gguf worker has no such thing natively — continuity there might mean a KV-cache snapshot the backend itself manages, or synthetic resume by replaying the stored transcript into a fresh context. Some clients may offer nothing, in which case the adapter's honest answer is "I can only replay." So the profile field is really a capability tier — native, synthetic, or none — and the backend's one language can promise only what the seated client's tier supports. That honesty matters for the patterns worth repeating: the two-lane engagement with cross-lane reconciliation worked precisely because lane B genuinely carried lane A's context; a synthetic-replay client could still run that play, but the backend should know it's paying transcript-length cost to do it, and a no-resume client shouldn't be handed a two-lane brief at all.

# well i think that non-gguf agents like agy, claude and codex all probably expose a similar level of resume semantics that essentially boil down to pointing to a session identifier of some sort to pull that session and its context. you're right about GGUFs and in that case it would point to a different abstraction in my opinion, one that could be coordinated with the other kind, but by their nature gguf models don't have this native notion, which is an important distinction pointing to two separate resume concepts and i would probably name them differently, reserving one notion for the native resume that most frontier models would expose

That's a cleaner cut than my capability-tier framing — not one axis with grades, but two genuinely different concepts that deserve different names. And the deep difference is ownership of state: in the native kind, the client holds the session and the backend holds only a pointer into someone else's store; in the gguf kind, there is no someone else — the backend's own journal _is_ the session record, and continuity is something para-agent reconstructs rather than requests. Naming them separately keeps the abstraction from ever quietly promising equivalence, because they fail differently too. The pointer kind fails by dangling — the client's store expired or moved, and the backend can't repair that, only detect it. The reconstruction kind can't dangle, since the backend owns the material, but it fails by fidelity: a rebuilt context is a _choice_ about what to rehydrate — the visible reply chain certainly, but thinking traces and tool results are exactly the streams your progressive-disclosure design keeps separate, so what gets replayed becomes a deliberate knob rather than an implicit given. Two concepts, two failure vocabularies — that alone justifies two names.

The coordination point you mention then lands naturally on the journal spine: a thread is identified by the spine regardless of which continuity mechanism carries it, and the turn record simply says which one — and per your naming instinct, the profile declares which concept its client speaks rather than pretending one subsumes the other. It also has a nice consequence for the frontier clients: since the backend journals everything anyway, reconstruction is available as a _fallback_ for them — a dangling session pointer degrades to a rebuilt-context continuation instead of a dead thread. The reverse is never true for gguf seats, which is the asymmetry that confirms these are two concepts and not one with grades: one mechanism can substitute for the other, but only in one direction.

# with GGUFs when i get to that, it would be running via llama.cpp, and i think that the default mode in general would be more headless one-shot-oriented , versus the more enriched persistent session interactions that i want for claude/agy/codex

That default lines up with the role split that's been implicit all along: the gguf seats are the worker tier — dispatch-shaped, stateless, parallelizable — while the enriched persistent sessions are the adjutant tier, where the value is precisely the accumulated context that makes cross-examination and multi-lane reconciliation possible. One-shot isn't a limitation of the gguf seats so much as the correct contract for the work they're intended to do: a repair or enrichment worker _should_ receive everything it needs in the dispatch and return everything it produced in the reply, because that's what makes it swappable and fan-out-able. It also means the reconstruction-continuity concept mostly stays on the shelf — it exists as an option for the rare gguf interaction that needs a second turn, but the default worker never touches it, which keeps that machinery from having to be load-bearing on day one.

The pleasing part architecturally is how little the core has to care. The exchange envelope is identical — prompt in, handle out, reply on completion — and a one-shot is just an exchange whose thread has exactly one turn; the journal spine records it with the same attribution and sequencing as an agy engagement, so the bookkeeping doesn't fork. The divergence lives where you've already put divergence: in the profiles. A llama.cpp profile declares one-shot default, no native resume, and its own invocation-versus-server-mode mechanics; the frontier profiles declare persistent sessions and pointer-resume. Even progressive disclosure scales down gracefully at the worker tier — a one-shot worker's "full trace" is barely more than its reply, so the collapsed default costs nothing there while the same tools still work uniformly. The two-mode picture ends up being one more instance of the pattern this whole design keeps converging on: one spine, one vocabulary, and all the genuine differences pushed into per-seat declarations.

That rereads the field notes in a useful way. The turn-6 "coped well with Bash denials" observation was recorded as resilience, but under your explanation it's agy gracefully absorbing a misprovisioned seat — the denials weren't all deliberate policy. There were really two overlapping regimes: the intended one (my explicit `--allowedTools Read Grep Glob` reviewer grants) and the accidental one (headless claude can't answer permission prompts, so anything not allowlisted resolves to deny — and if the workspace-local settings never loaded because the invocation wasn't anchored to the project root, the allowlists that would have said yes simply weren't in play). The fallback-to-grep-sampling cost was real — slower, sampling instead of running the thing — and a provisioned seat wouldn't have paid it. Worth flagging too that workspace anchoring has a _silent_ failure mode, which is worse than the loud one: `.mcp.json` resolves from the project, so an unanchored seat doesn't error about missing MCPs — the shared-MCP mounts just quietly don't exist, and the worker proceeds without capabilities it was supposed to have. Loud denial you notice; silently-absent tools you only discover by wondering why the output is thin.

The design landing spot is that workspace anchoring belongs in the seat's profile as a first-class field — the workspace root plus what's expected to resolve from it — and the exchange tool guarantees launch-from-root by construction, replicating exactly what you do manually when you cd before launching. That also upgrades the probe discipline from L1: reachability ("is the binary there, does it auth") isn't enough; the preflight should be a _provisioning_ probe — does the seat actually see the settings, permissions, and MCP servers its profile says it should. The Antigravity skill's cheap "reply OK" probe checks the first tier; a "list your MCP servers / confirm tool X is available" probe checks the second, and it's the second that would have caught this class of friction before a $5 engagement ran degraded. It slots cleanly into the shared-MCPs coordination story too — the config declares what both sides should mount, and the provisioning probe is how the backend verifies the declaration actually took effect on the worker side rather than trusting the projection worked.
