
Byte spans and byte sizes should all be expressed in raw binary traditional bytes e.g. 1024 = 1 KiB for clarity and precision 

Packing needs to take into account header and cumulate per-record bytes including all container formatting, row delimiting etc. because all of this counts towards the total written file's bytes. The point of this is that readers (LLMs) often have read token limits well beyond their context horizon and depending on the reader, the size of the file needs to be below the preview truncation threshold, lest they may inadvertently read a truncated file. 

The heuristics for for packing (greedy,balanced,loose) can go. Ultimately my general goal is to pack as tightly as possible, so maybe its best to focus on simply working out the minimal packing. There's also the complexity of different grouping strategies and the importance of keeping items within a group, with sorting/order being secondary within a group. perhaps maybe i would introduce a different kind of knob which either allows or disallows flexible packing order within groups. "Flat packing" mode where there is no grouping specified is still logically a single group, so its not a special case. For the option where sorting is enforced (unflexible packing order), we aim pack items as tightly as possible while respecting the MaxBytesSpan quota specified for shardfile total content bytes, which takes into account the header bytes and all of the rows that would be written to a file. We could also incorporate a strict vs non-strict packing option with the headroom parameter allowing for some number of bytes allowed beyond the target quota e.g. if there are 3 candidate files for 3 rows of data and the target quota is 32,768 bytes, if the header row was 1024 bytes, first file is 16384, second filie is 8192, third file is 4096 bytes, the total is 29696 bytes, which is less than the 32,768 target bytes. In this case we could close the shard if adding an additional record would exceed the target in strict mode or allow an additional record if the next target is within tolerance beyond the quota. In this second case, if tolerance was 8192 and the 4th record amounted to 4096 then it would be packed into the shard as a fourth record. If the candidate fourth record was 8192 with the given target and headroom, it would still be admissible because we had some slack left over from the first 3 files. However, with tolerance, a 4th record that is exceeds size of quota remainder + tolerance headroom e.g. 32768 (quota)-29696(cumulative bytes before 4th candidate entry)+8192(headroom tolerance)= 11264 bytes, it would not be admissible.
