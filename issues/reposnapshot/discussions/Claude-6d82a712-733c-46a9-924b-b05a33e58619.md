## The workflow, conceptually

LTS's emission is five passes — render, arrange, emit, measure, navigate — but the passes aren't the problem. Six structural inversions are, and each one is a thing a verbatim port would import.

**1. The row grammar is written three times.** Lines `:2318`, `:2461`, `:2501` each contain an independent format string for the same row — six variants counting the `includeAttributes` branches. They must agree byte-for-byte or the offsets point at the wrong bytes, and nothing checks. The format's grammar is not expressed once anywhere in the codebase.

**2. Offsets are recovered rather than recorded.** `Get-EntryByteOffsets` regex-matches `"content":"…"` out of already-serialized JSON to find where content sits — the writer knew, discarded it, and parses it back. The `.txt` path is the same instinct in gentler form: it re-renders the meta prefix (`:2501`) and re-counts its bytes *after* writing the line. The correction is one inversion: **positions are a receipt of the write, not a measurement of the artifact.** That alone deletes `Get-EntryByteOffsets` and the third render.

**3. Flat and grouped are two different programs.** Flat buffers the whole corpus, computes cut points, `BlockCopy`s slices, and derives offsets as `shardHeaderBytes + (row.ByteStart - cutStart)`. Grouped calls `Partition-Files`, opens a `FileStream` per shard, re-renders every row, and tracks a running `$currentOffset`. Same output format, two implementations, two offset formulas — and `$cutStart`, defined only in the Flat branch, is referenced from the shared tail. Conceptually: **grouping decides membership, not how bytes get written.**

**4. Buffer-everything.** A 4 MB `StringBuilder` holding the entire corpus, then `$enc.GetBytes($sb.ToString())` materializing a second full copy as bytes — both live simultaneously alongside the entries. This is what caps corpus size for the virtual-DB use case.

**5. The schema is hardcoded, which contradicts the format's own doctrine.** Two literal schema strings selected by a boolean. But `shard-format-notes.md` says readers "parse exactly what the header declares — never a fixed column set." V3 entries are *open bags* with an observed element set, so the writer should **derive the schema row from the elements actually present**. That's the open element model reaching the writer — and it's what makes "header and rows always agree" true by construction instead of by discipline.

**6. The tree is built from a different population than the rows.** `:2541–2545` derives `$allPaths` and `$fileSizeMap` from `$snapshot.files` while the rows came from `$rowManifest`. Under lean-payload routing those populations diverge — and the doctrine requires routed entries to be absent from the tree too. The tree must be built from **the rows that were actually written**.

Two smaller warts in the same family as the ones you caught: `Build-DirectoryTree`'s `$MaxDepth = 6` is a **dead parameter** (declared, never referenced in the body), and `omitted_counts.dirs` is initialized and never incremented — so the tree silently truncates at `MaxFilesPerDir` while reporting only half of what it dropped.

## What the operations actually are

Stated free of LTS's layout, the stage does seven things:

| # | operation | owner |
|---|---|---|
| 1 | **decide the schema** — from the observed element set | shared declaration |
| 2 | **order** — grouping, packing, global idx | `shards` |
| 3 | **encode** — content → codec → span + record of which substitutions fired | `serialize` |
| 4 | **frame** — meta + length prefix + span = one row, grammar expressed *once* | `serialize` |
| 5 | **place** — write rows into shard files; positions fall out of writing | `serialize` |
| 6 | **index** — position receipts + paths → tree | `manifest` |
| 7 | **declare** — schema row, Compaction key, summary, instructions | `manifest` |

Note where that lands step 1: the schema is consumed by *both* the shard header row and the tree's `ColumnHeader`, so it's computed once upstream and handed to both. That's the thing that makes header/row agreement structural. And step 3 naturally produces the Compaction receipt as a byproduct — the "substitutions actually made" that ledger #16 requires is just what the codec logged, not a separate pass.

## Dropping `\\` gets you the thing you rejected substitution for

`shard-format-notes.md` names the invariant that separated the two schemes: *substitution never rewrites a character of the source — it only adds marks where line breaks were; backslash escaping alters existing characters.* That was the strongest argument against `\`, and it's the whole reason Control Pictures stayed on file.

Drop self-escaping and that distinction disappears. `\` also only adds marks at line breaks. Literal backslashes pass through verbatim, so `"C:\Users\me"` renders as itself rather than `"C:\\Users\\me"` — you get substitution's defining virtue at ~1 token instead of 3.

What you give up is decodability at the ambiguous sites: source containing a literal backslash-n becomes indistinguishable from an encoded line break. Measured on the production C# payload, that's the `\\` row — **127 sites across 70 shards, ~1.8 per shard**. And in most of those the source's `\n` was already *semantically* a newline inside a string literal, so a reader resolving it as a line break is right anyway. The genuinely wrong reading is Windows paths, and it's rare.

Under a no-rehydration posture that trade is obviously correct: showing the source verbatim beats being reversible.

## The resulting codec

Line breaks are the container's problem, not the content stage's — that's the one piece I'd keep unconditional. `format-ws`'s `lf` op normalizes CRLF inside content; the container must encode *whatever line breaks remain*, because a raw newline breaks the row invariant. Different jobs, same character. If the serializer delegated it, a profile without `lf` would emit a broken artifact.

- All line terminators — LF, CRLF, CR, NEL, LS, PS, VT, FF — collapse to `\n`. One marker, no preservation of kind.
- `\` passes through verbatim. Never doubled.
- Remaining C0 + DEL: stripped.
- TAB: literal. Indentation stays `rs-indent`'s.
- Compaction block becomes a notice, not a key: *line breaks normalized to LF and encoded as `\n`; control characters stripped; content is not byte-reconstructable.*

## The axis that matters: format-ws is lexically blind

It can't tell code from string-literal content. So "breaks code" splits in two, and the second is the dangerous one:

- **structure** — does it change syntax/semantics of the code itself?
- **data** — does it change bytes *inside string literals*?

Data damage is invisible. The file still compiles; it just means something different, or a fixture stops matching. `rs-psstrip`/`rs-csstrip` have string-masking machinery precisely because they operate inside lines. `format-ws` has none.

## The three sensitive ops

| op | implementation | why it's sensitive |
|---|---|---|
| **`nfc`** | `.Normalize(FormC)` | Rewrites every decomposed sequence in the file, string literals included. `"café"` as `e`+combining-acute becomes precomposed `é` — different bytes, different length, different equality at runtime. Any file that *tests* Unicode normalization gets its test data normalized and is now testing the wrong thing. Not a whitespace operation at all. |
| **`trim-inner`** | `(?<=\S) {2,}(?=\S)` → `' '` | Collapses space runs inside string literals: `"Name:    value"` → `"Name: value"`. Kills embedded SQL formatting, fixed-width templates, ASCII art, aligned output strings. The `\S` lookarounds do protect indentation, so leading whitespace is safe — the residual exposure is purely intra-line data. |
| **`strip-zwsp`** | deletes U+200B/200C/200D/2060/FEFF | **U+200D (ZWJ) and U+200C (ZWNJ) are load-bearing characters**, not invisible noise. ZWJ composes emoji sequences; ZWNJ changes word forms in Persian/Arabic/Indic. Deleting them inside a literal corrupts data — `"👨👩👧"` becomes three separate people. Emoji in source strings is routine (LTS itself uses 📁 📄 ✂️). |

Note what these three have in common: **they're the ops that aren't whitespace operations.** NFC is character normalization, strip-zwsp is character deletion, trim-inner is intra-line respacing. The whitespace-structural ops all stay at line boundaries and margins.

Also worth knowing: `strip-zwsp`'s original justification partly rested on *reserving* the invisibles for the codec sigil. That rationale died yesterday — the codec uses `\`. The op has lost one of its two reasons to exist.

## The structural ops — safe, with one shared exposure

`trim-trailing`, `max-blank-2`, `max-blank-1`, `trim-doc` touch only line ends and document margins. Their single failure mode is **content inside multi-line raw literals** — here-strings, C# verbatim strings, Python triple-quotes, JS template literals — where trailing spaces and blank-line runs are data. ## NFC

**Bound the fear first.** NFC is the conservative form — canonical composition only, no compatibility mappings. It won't turn `ﬁ` into `fi` or `½` into `1⁄2` (that's NFKC). It's a no-op on pure ASCII, which is most source. Unicode's Normalization Stability Policy also guarantees it's idempotent and stable across versions, so re-running is safe. The common fears are mostly unfounded.

The real hazards are narrower and sharper:

**It changes string identity.** `"café"` as `e`+U+0301 becomes `é` U+00E9 — different bytes, different `.Length`, different equality unless the comparison normalizes. A fixture with decomposed data now has composed data.

**The self-referential case is the bad one.** Any file that *tests* Unicode handling contains deliberately decomposed/composed pairs, and NFC destroys the distinction the test exists to check. That's the tool corrupting the thing being measured — and it lands directly on your stated contract, since carrying code to be debugged includes carrying Unicode bugs.

**Identifiers, for illustration.** JS compares identifiers by code point with no normalization, so decomposed and composed `café` are genuinely different identifiers. Normalizing a whole file is self-consistent so nothing breaks *within* it — but it shows NFC changing program-visible identity, not just presentation. (Python normalizes identifiers to NFKC itself, so it's immune.)

**The one I'd actually fix: the receipt can lie.**

```powershell
try { $t = $t.Normalize([System.Text.NormalizationForm]::FormC) } catch {}
```

`String.Normalize()` throws `ArgumentException` on ill-formed UTF-16 — unpaired surrogates. The empty catch swallows it, which is *correct* degradation under never-fail-ingest. But `Processing` still records `nfc` as having run. A receipt claiming a fold that didn't happen is worse than no receipt, and it's the inverse of the principle you already hold about unaudited folds.

## strip-zwsp

The op treats five characters as one class. They're three classes, and the name is taken from the safest member.

| char | what it is | strip? |
|---|---|---|
| U+200B ZWSP | line-break *opportunity* hint | safe — purely presentational |
| U+2060 WJ | no-break hint | safe — purely presentational |
| U+FEFF ZWNBSP | deprecated word-joiner (BOM at position 0) | safe |
| **U+200D ZWJ** | **composes emoji sequences; forces Indic conjuncts** | **content** |
| **U+200C ZWNJ** | **separates morphemes in Persian/Arabic/Urdu/Hindi** | **content** |

Strip the ZWJs from 👨👩👧 and you get three separate people. 🏳️🌈 becomes a white flag and a rainbow. In Persian, removing ZWNJ from میخواهم changes the word. These aren't invisible noise — they're the only thing distinguishing one string from another.

Exposure in a code corpus is real but concentrated: emoji in UI/CLI strings and test fixtures, and — the self-referential case again — **any library that processes emoji sequences or Indic text has these characters in its fixtures by necessity.**

**The redundancy:** `strip-zwsp` is unanchored and includes U+FEFF, so it subsumes `no-bom` entirely. With both in the defaults and `no-bom` running first, `no-bom` is dead — `strip-zwsp` would catch that BOM regardless.

**The off-target finding, which I think is the most interesting one.** If the rationale is sanitizing invisibles for legibility and clean tokenization, the current set misses in both directions. It strips two characters that carry meaning — and it does *not* strip the bidi controls U+202A–U+202E and U+2066–U+2069, which are invisible *and* actively hazardous. Those are the Trojan Source vector (CVE-2021-42574): they make source **display differently from how it executes**.

For a payload whose entire purpose is being read by a model to reason about code, that's the failure mode that matters most — the reader sees one program, the compiler sees another. It's unaddressed today, and it's a stronger argument for an invisible-stripping op than anything ZWJ removal buys.

**Per-item I/O.** `format-ws` runs once per file. A store read per invocation is N reads per run, and there's no caching seam — `bag-helpers`' closure rule is explicit that module-scope state doesn't cross the runspace boundary, and each worker runspace is independent.

**No mechanism exists.** Injecting a table would mean adding `SessionStateVariableEntry` support to colonel: new `Compile-Plan` surface, new validation, new failure modes. Real work for three code points.

**It breaks reproducibility, which is load-bearing here.** Snapshots are exchange artifacts whose output must not vary with the producing machine — that's the stated reason for the zero-dependency bent. A processor reading an external table makes payload content a function of that file's presence and version. A missing or stale store changes the artifact silently.

There *is* a no-new-machinery variant: pass the table through `$Config`, which processors already take. But then every caller must supply character tables, and a processor without one needs embedded fallbacks — which puts the tables right back in the code and gives you two sources of truth instead of one.

## What bidi controls are

Nine invisible characters that control text *direction* — needed because Arabic and Hebrew run right-to-left while Latin runs left-to-right, and mixed text needs disambiguation:

```
U+202A LRE   U+202B RLE   U+202C PDF   U+202D LRO   U+202E RLO
U+2066 LRI   U+2067 RLI   U+2068 FSI   U+2069 PDI
```

They reorder how characters are *displayed* without changing the order they're *stored* in. Trojan Source (CVE-2021-42574) weaponizes that: embed them in a comment or string so the code displays one way and compiles another — a reviewer sees a comment where the compiler sees a `return`.

## Your point kills most of it, and I overstated the concern

I called it "the strongest remaining read-integrity gap." That imported a threat model without checking it against who actually reads these payloads.

Bidi is a **presentation algorithm** (UAX #9). Files store logical order; only a rendering engine reorders. A model consuming a payload reads the byte sequence in file order — **logical order, which is exactly what the compiler sees.** The display/execute divergence that makes Trojan Source work requires a renderer in the path, and there isn't one. The attack targets human review in an editor or a diff view.

So the concern is a rendering concern, and rendering has no provenance here. You're right.

## And it likely inverts

Where bidi controls actually appear in real corpora, it isn't attacks — it's i18n resource files and any source carrying mixed Arabic/Hebrew string literals, where they're **load-bearing content**. Stripping them corrupts the data.

That puts them in decision #15's category, not the strip list: characters that look like invisible noise but carry meaning. The same self-referential test applies — a library handling RTL text has them in its fixtures by necessity.

**[schema-derivation-brief.md](issues/reposnapshot/briefs/schema-derivation-brief.md)** — the harder one, and the crux turned out to be sharper than "derive the columns."

The format is positional, so every row in a shard needs the same column count. An element on only some entries forces a real choice, and **per-shard schema** looks right because it composes with grouping instead of fighting it: under `ByFileType` a shard is homogeneous by construction, so a language-specific element is present on every row of that shard or none, and the header says which. A 30% corpus-wide coverage number becomes 100% in three shards and 0% in the rest. That also gives `Header.Elements` a cleaner job — corpus-level coverage diagnostics, while each shard's header row is the local truth its rows must match.

Its exit gate includes the claim that's never been tested end-to-end: **an entry carrying a novel element reaches the payload as a column with zero writer changes.** That's the open element model's whole promise, currently unexercised.

## Sequencing

Stated rather than hidden: the renderer consumes a schema, so the schema *contract* precedes it while the *derivation* can land after. Defensible order — freeze the schema object's shape, build the renderer against a fixed instance, then land the derivation. That keeps both independently landable and stops the row work stalling behind the harder design.

Which also answers your original fork: it isn't either/or. Schema contract first, then row grammar, then derivation.

## What changed in the brief

**Recommendation downgraded** from BOM-sniff-plus-heuristic to **BOM-sniff-only**, with the heuristic kept as option (c) and explicitly not recommended.

The reason is the sequencing you pointed me at. Detection can't simply be added — the NUL guard runs on raw bytes before any decode, so anything that recognizes UTF-16 has to run *ahead* of it, or UTF-16 still halts. That reorders the load-bearing lines in the file with no dedicated suite, and it changes what the guard *means*: "contains NUL" is evidence of binary only for a byte stream believed to be 8-bit text.

A BOM makes that safe, because it's unambiguous evidence — the guard's semantics shift only where something authoritative said "not 8-bit text," and every other path keeps today's behavior exactly. The heuristic version makes a fallback guard defer to a *guess*, which inverts the relationship you just described.

Three options now, cheapest first: **(a)** rename only, no detection; **(b)** BOM sniff only; **(c)** BOM plus heuristic.

**Two new exit-gate assertions**, both about proving the reorder didn't weaken anything:

- a genuinely binary file still halts
- a BOM-less UTF-16 file still halts under (b) — asserted deliberately, so the residual gap is a recorded choice rather than a later discovery

**Non-goals gained "redesigning binary exclusion"** — that's the extension blacklist's job, it costs no I/O, and it works.

I'd also downweight the urgency I gave this. Modern PowerShell, VS Code and `Set-Content` all default to UTF-8, so UTF-16 `.ps1` is a legacy-corpus concern rather than a live one. Option (a) is more defensible than I first made it sound: it makes the field honest, touches nothing risky, and forecloses nothing.

## The framing error, precisely

You're right that it's a skip, not a halt — and the structure shows the conflation:

| stream | members |
|---|---|
| `IR.Skipped` | `FileTooLarge`, `ExtensionBlacklisted` — policy exclusions |
| `IR.Diagnostics.Routed` | `BinaryOrNulContent`, `EmptyFile`, `EmptiedByProcessing`, exception messages |

`BinaryOrNulContent` is the **third member of the exclusion family** — the same decision `ignore` would have made, deferred only because it needed bytes to make it. But it's expressed as `ReadError` + `_ChainHalt`, so it lands in `Routed` beside genuine failures instead of beside its siblings in `Skipped`. The payload doctrine asks that distinct reasons survive to the sidecar; an auditor currently can't separate "excluded by policy" from "couldn't read" without string-matching the reason.

That fix is free — it's vocabulary and routing, no change to the read budget.

## On pulling detection forward

Worth being honest about the cost, since it cuts against the constraint you're protecting. For `ingest` to *route* on binary-ness, the fact must exist before dispatch — and it only exists after bytes. So it needs a bounded prefix read at discovery, which is **an extra open on every file to save a full read on the rare one that slipped the blacklist.** Given how comprehensive the blacklist is, that's paying ~100% to save <1%.

The version that doesn't fight the budget: keep the single read where it is, and let file-read stamp what it learned — `Encoding`, `IsBinary`, `HasBom` — as descriptor metadata. Ingest can't consume it this run, but **assemble** can, and assemble is where the routing decision actually lives. Same information, same one read, no re-sequencing.

Where a prefix read *would* pay for itself is if the ceiling ever rises or the corpus gains large unenumerated binaries — worth recording as the trigger condition rather than the default.

# and why can't ingest consume information from stages that happen earlier to it? the point is to only ingest files that are allowed to be ingest, hence the final stop gap in ingest with NUL bytes

You're right, and my "can't consume it this run" was wrong. Ingest consumes upstream descriptor metadata by design — that's exactly how `SizeBytes` and extension already work: crawler stamps, ignore filters on the stamp, ingest dispatches what survived. Nothing stops another stamped field joining that set. The constraint is **production** timing, not consumption.

So the real question is where the fact can be *produced*.

One clarification that matters for the answer: the NUL check isn't in the ingest stage — it's in `file-read.ps1`, the chain's head processor, which colonel runs *after* ingest dispatches. So today the stop gap fires downstream of the stage that would want to act on it.

## Where it could be produced

**(i) Bounded prefix sniff at discovery.** Crawler (or a pre-ingest step) opens, reads the first N bytes, stamps `IsBinary` / `Encoding` / `HasBom` onto the descriptor. Ignore or ingest then rejects binaries as a metadata filter — same shape as `ExtensionBlacklisted`, in the same Skipped stream, before any full read. Costs one extra open per file.

**(ii) Sniff inside the existing open.** `file-read` opens a stream instead of `ReadAllBytes`, checks the prefix for NUL and BOM, bails before reading the rest if it's binary, otherwise continues. No extra open, and it makes the stop gap actually gate — today it rejects a file only after paying the full read for it. Your own comment in `file-read.ps1` already flags this ("may benefit from streaming read if large files are expected"), parked because the `MaxSizeBytes` ceiling bounds the waste.

The thing (ii) doesn't give you is ingest owning the decision.

## Which matters depends on the goal

If the goal is **"only allowed files get ingested"** — that already holds. Binary files never become entries; they're rejected at read time and routed out. (ii) makes that rejection cheaper and earlier without touching the pipeline shape.

If the goal is **"the decision belongs to the stage whose job is admission"** — that's an architectural claim, not an efficiency one, and it's the one that justifies (i)'s extra open. It has a real payoff I under-weighted: it puts `BinaryOrNulContent` in `Skipped` beside `FileTooLarge` and `ExtensionBlacklisted` *by construction*, rather than needing the vocabulary fix I proposed as a patch. The taxonomy stops being something to maintain and becomes a consequence of where the check lives.

That second framing is probably what you're reaching for, and it's stronger than the efficiency argument I was measuring it against. It also ports well — a Node successor doing discovery-time sniffing gets the same clean split.

What do you want recorded: the sniff-within-one-open improvement as a near-term item, the discovery-time detection as a design direction with its cost stated, or both as alternatives in the encoding brief?

Crawler walks the entire tree and ignore filters afterward — so sniffing at crawl time would open `.git`, `node_modules`, build output, everything ignore is about to throw away. So the role division you described holds, but content-derived metadata has to be split off from stat-derived metadata:

- **Free metadata** (size, mtime, path, extension — one `FileInfo`) → crawler, eagerly, for everything
- **Paid metadata** (binary-ness, encoding) → only for candidates that survive the free filters

## Recommendation: sniff in ingest, before dispatch

**Ingest already owns the merged exclusion stream** — `rs.core.ingest.psm1:32` merges ignore's `FileTooLarge` / `ExtensionBlacklisted` into its own `Skipped` output. So this adds a reason to your existing framework rather than building anything: same stream, same merge, same consumer. It's also literally the stage named for admission, which is your "final stop gap in ingest" put where the name already promises it is.

The economics work because the free filters run first. On a repo walking 10k files where 1.5k survive ignore, you pay **1.5k prefix opens, not 10k** — which is the whole reason placement matters more than whether to do it at all.

Three things fall out, all simplifications:

**`BinaryContent` joins `Skipped` by construction.** No vocabulary patch, no re-typing `ReadError` — the exclusion is made by an exclusion stage, so it lands beside its siblings automatically. The taxonomy problem I proposed patching just stops existing.

**You don't need to stamp `IsBinary` at all.** If ingest excludes binaries, every descriptor reaching the chain is non-binary *by construction*. Only `Encoding` rides forward. That's less metadata, not more.

**`file-read` stops asserting.** It decodes with a stamped, measured encoding instead of hardcoding UTF-8 — which closes the encoding brief's item 2 without file-read doing any detection. Its NUL guard becomes belt-and-braces; keep it (it's free, the bytes are in hand) with the understanding that **if it ever fires, upstream policy leaked** — a much more useful signal than what it means today.

## The alternative, and when I'd pick it

If the extra open is unacceptable, do the sniff inside `file-read`'s existing open — stream, check the prefix, bail before reading the rest. Zero extra I/O, and it makes the guard gate properly instead of firing after a full read. What you lose is admission living in an admission stage, and you keep needing the reason-vocabulary fix.

I'd take the ingest version. The cost is bounded by the survivor count, and it buys the property you actually asked for: policy enforced by the stage that owns policy, using machinery that already exists.

One caveat on my confidence — I've read the Skipped/merge seam but not the full exclusion framework and "update logic" you mentioned. If that framework already has a designated home for content-evidence exclusions, slot it there rather than taking my word on ingest.
